# Security Review

Internal code-level review performed on this codebase. **This is not a professional third-party security audit** — treat it as a documented starting point, not a certification. See "Remaining risks" below for what still needs independent review before handling real funds or user accounts.

## What was inspected

Server-side data fetching (`src/lib/market/*.server.ts`), the API envelope/error layer (`api.server.ts`), every `/api/market/**` route's input validation, XSS/dangerous-sink usage repo-wide, external-link handling, own-route rate limiting, HTTP security headers, error-reporting/logging code, route-param validation, and `.gitignore` secret hygiene.

## Findings and fixes

## Already correct (verified, no change needed)

- Every external API response is validated with Zod before use; no `as Type` cast reaches the client unvalidated.
- Error responses to the browser are always generic, pre-written strings — no upstream error text, stack trace, or internal file path is ever interpolated into a response body.
- API keys are read only via `process.env` in `.server.ts` files, never via `import.meta.env`/`VITE_*`, and are never echoed back to the client.
- Every `/api/market/**` route calls `guard()` first — 90 req/60s per-IP rate limiting.
- No `dangerouslySetInnerHTML` with external/dynamic content, no `eval`, no `document.write` anywhere in the app.
- The single `target="_blank"` link (social links in the footer) correctly pairs `rel="noreferrer noopener"`.
- Server-side error capture (`error-capture.ts`) logs full stack traces server-side only; the client-facing error page is static with no dynamic detail.

## Post-deployment update (robinpl.vercel.app)

The site is now live on Vercel. Several items from the original "remaining risks" list below are resolved as of this update:

- **Security headers**: set via Nitro `routeRules` in `vite.config.ts` (not a top-level `vercel.json` — that file is silently ignored by `vercel deploy --prebuilt`, which only reads the generated `.vercel/output/config.json`; routing headers through Nitro's own config is what actually lands in that file on every rebuild). `Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`, and `Permissions-Policy` are set on every route; Vercel's platform edge adds its own `Strict-Transport-Security`. Verified live via `curl -I https://robinpl.vercel.app/`.
  - `script-src` had to include `'unsafe-inline'` — TanStack Start's SSR hydration payload is an inline `<script>` with no nonce/hash infrastructure in this app (would need per-request nonce generation wired through the Nitro render pipeline; out of scope here). This was caught by testing the deployed site with Playwright *after* the first CSP deploy, which showed the app fully broken (`Invariant failed` on every route) until this was added. The still-meaningful protection this CSP keeps is the external-script allowlist (only `s3.tradingview.com`) and the `frame-src` allowlist (`dexscreener.com`, `tradingview-widget.com`, `s.tradingview.com` — TradingView's widget opens iframes from two hosts, not one, also only discovered by testing the real embed post-deploy).
- **`lovable-error-reporting.ts`**: re-confirmed at deploy time — `window.__lovableEvents`/`window.__lovableReportRuntimeError` are only ever populated inside the Lovable.dev editor iframe. On the deployed site these are `undefined`, so every call is a no-op. No live endpoint is wired. Confirmed safe.
- **Dependency audit**: `npm audit` shows 0 vulnerabilities in production dependencies. The 5 high-severity findings are entirely in a **devDependency-only** chain (`brace-expansion` → `minimatch` → `@eslint/config-array`/`eslint`), reachable only by running ESLint locally — never shipped in the deployed bundle. `npm audit fix` (non-force) cannot resolve it; only `--force` can, which bumps ESLint to v10 as a breaking major-version change to the lint config. Deferred deliberately — no production security benefit to justify a breaking lint-tooling upgrade right now.
- **`eslint.config.js` was missing `.vercel` in its ignore list** — once `.vercel/output`'s hundreds of generated build files existed locally, `npm run lint` hung for 90+ seconds instead of the normal ~3s (glob-walking the generated output tree). Fixed by adding `.vercel` alongside the existing `dist`/`.output`/`.vinxi` ignores.
- **Routing bug found post-deploy, unrelated to security**: adding `src/routes/token.tsx` (the static `/token` announcement page) in an earlier session silently broke every `/token/$chainId/$address` on-chain token detail page — TanStack Router's file-based routing treats any `token.tsx` as a *layout* for the whole `token/*` segment, so the pre-existing dynamic route became an orphaned child with no `<Outlet />` to render it in, and the layout's own content showed instead on every Robinhood Mainnet token page. Confirmed live via Playwright (`h1` text checked, not just HTTP status — the SSR `<title>` was correct even though the wrong component rendered, so a status-code-only check would have missed this). Fixed by splitting into three files: `token.tsx` (pathless layout, renders only `<Outlet />`), `token.index.tsx` (the announcement page, exact-match `/token`), and the untouched `token.$chainId.$address.tsx` — now proper siblings under the layout.

## Remaining risks (require infrastructure or a professional audit to fully close)

- **In-memory state on serverless (Vercel-specific)**: both the rate limiter (`http.server.ts`) and the AI feed's rolling event store (`src/lib/feed/engine.server.ts`) hold state in module scope. On Vercel Functions this persists across warm invocations of the *same* function instance, but is **not guaranteed across cold starts or concurrent instances/regions** — under real multi-region traffic, different requests can hit different instances with different in-memory state, so the rate limiter under-counts and the feed's "conversation grows over time" behavior becomes less consistent than on a single long-running process. Not fixable without a shared store (Vercel KV/Redis) or a real database; the feed already degrades honestly (never fabricates history to compensate), so this is a consistency/scale limitation, not a correctness or security bug.
- No automated dependency vulnerability scanning is wired into CI (no GitHub Actions/Dependabot — there's no git repo yet, only a direct `vercel deploy --prebuilt` pipeline). Recommend adding once the project is pushed to a git host.
- A professional penetration test / third-party security audit has not been performed and remains out of scope for this review.
